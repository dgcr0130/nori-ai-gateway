# RAG 문서 작성 규칙

## 적용 대상과 기준

RAG는 질문과 관련된 문서를 찾아 답변의 근거로 주는 방식이다. 이 규칙은 TC부터 nori-mes·nori-hrm까지 각 시스템의 검색 원문을 새로 작성하는 사람이 따른다. 기존 매뉴얼을 그대로 반입하지 않고, 코드와 대조한 사실을 이 규칙에 맞는 Markdown으로 쓴다. 기준은 [006 SPEC](../../nori-sdd-specs/work-items/006-ai-gateway-redesign/spec.md)의 4.1·4.3~4.9·5절·7절이다.

이 문서는 작성자를 위한 안내이며 검색 원문이 아니다. [TC 문서 목록](tc-rag-document-list.md)도 검색 원문에 넣지 않는다. 예시를 감싼 바깥 코드 울타리, 긴 설명과 비교표는 안내 문서의 표현이다. 실제 반입 파일에는 아래의 크기·문법 규칙을 적용한다.

006 구현 계획의 phase 5에서 Markdown 추출·마스킹·기동 동기화·색인 활성화 경로를 작성했고, `config/ai-gateway.yaml`의 TC 문서 원천은 `00.rag/user/`·`00.rag/admin/` 두 개다. 로컬 단위 시험과 DB 통합 시험 결과는 중앙 PLAN의 phase 5 기록으로 구분해 확인한다. phase 6에서 추론 활성 모드의 규칙 검색·부모 선택·충분성·한 번 재검색을 연결했으며 `CoreBeansConfiguration.knowledgeDocumentStateReader`는 활성 메모리 문서의 revision과 현재 권한을 확인한다(추론 비활성 모드는 기존 fail-closed 상태 조회를 유지한다). phase 6 시험 결과는 중앙 PLAN의 phase 6 기록에서 확인한다. 작성한 문서의 실제 반입·검색 성공은 별도 확인이 필요하다.

## 문서가 검색과 답변으로 바뀌는 방식

| 작성자가 알아야 할 단위 | 목표 동작과 작성 이유 |
|---|---|
| 문서 제목 | 첫 블록인 H1 하나가 문서 제목이다. 제목은 직렬화 후 1~60자이다. 검색 때 절 제목과 함께 붙으므로 대상 업무를 드러낸다(006 SPEC 4.4 표의 문서 제목·문맥 헤더 행). |
| 절과 부모 | H2부터 다음 H2 전까지가 한 절이다. H2와 메타 블록을 뺀 본문 전체를 부모라고 하며 1~450자이다. LLM에는 검색된 작은 조각 대신 이 절 전체를 주므로 조건과 결론을 함께 쓴다(4.4 절·부모 청크 행). |
| 검색 조각과 자식 | 문단 하나, 최상위 목록 항목 하나와 하위 항목 전체, 표 자료 행 하나, 코드 블록 하나가 각각 자식이다. 메타 블록을 빼고 직렬화한 자식은 1~200자이고 자식마다 정확히 한 부모에 속한다. 최상위 목록 항목과 하위 항목 전체에 이 상한이 걸리므로 긴 목록을 한 항목에 몰아넣지 않는다(4.4 자식 청크 행). |
| 문맥 헤더 | `문서 제목 > 절 제목`을 자식 앞에 붙여 검색하고 부모 앞에도 붙여 제공한다. H2도 직렬화 후 1~60자이고 파일 안에서 유일해야 한다. 같은 값의 주체를 구별하도록 제목에 실제 대상을 쓴다(4.4 문맥 헤더 행). |
| 인용 | 위치는 `bucket·objectKey·revision·section·lineFrom·lineTo`이다. section은 직렬화한 H2이며 원문 줄은 1부터 시작하고 양끝을 포함한다. 부모는 H2 줄부터 마지막 블록 끝 줄, 자식은 해당 블록의 첫 줄부터 끝 줄이다. 인용 안정성을 위해 불필요한 줄 이동을 피한다(4.4 인용 위치 행). |
| 파일 제외 | 규칙 위반·크기 초과·미지원 파일은 파일 전체를 색인에서 뺀다. 정상 절만 따로 살아남지 않으므로 한 절의 위반도 반입 전에 고친다(4.4 제한 행 뒤 설명·5절). |
| 반영 시점 | 최초 기동·재기동에서만 파일을 읽고 새 색인 묶음을 활성화한다. 실행 중 수정은 반영되지 않으므로 업로드 완료와 검색 반영 완료를 구별한다(4.4·7절 문서 반영 시점). |

450·200·60자는 임의 요약 길이가 아니다. 006 SPEC 4.4의 크기 근거는 근거 예산 3072토큰에서 비문서 몫 384토큰을 남기고 부모 6개에 각각 448토큰을 배정한다. 부모 헤더 몫 96토큰을 빼면 본문 352토큰이고, 자식은 헤더 포함 256토큰 중 본문 160토큰이다. 한국어 표본의 최대 0.715토큰/자 비율로 바꾸어 50자 단위로 내린 본문 상한이 450·200자이다. 두 제목과 구분자 123자는 약 88토큰으로 헤더 몫 안에 들도록 제목별 60자를 정했다. 정답률 보증값은 아니며 실제 선택은 번호·위치·헤더를 포함한 전송 토큰 수로 한다.

이 값은 목표 초기 상한이다. 설정은 `ai.gateway.documents.childMaxChars=200`, `parentMaxChars=450`, `headingMaxChars=60`이며 각각 1~초기값으로 낮출 수 있다. 작성 전 담당자에게 적용값을 확인하고 더 낮으면 그 값을 지킨다. 이유는 4.4의 허용 범위 안에서도 작성 가능한 길이가 달라지기 때문이다.

검색은 의미·키워드·식별자 경로를 합친다. 식별자는 영문·숫자·밑줄·점·하이픈의 연속 토큰 중 숫자를 포함한 토큰과 입력 대상 참조 전체이며, 일반 숫자 단독도 정확값으로 찾는다. 정규화는 NFC·영문 소문자·연속 공백 하나이고 숫자·밑줄·하이픈을 지우지 않는다. 숫자 없는 모든 코드를 별도 정확 검색한다고 가정하지 않는다. 원문 코드와 실제 업무 명사를 함께 써야 하는 이유이다(006 SPEC 4.5).

충분성 검사는 질문의 식별자·대상 참조 전부와 주요 명사 중 `min(2,명사 수)`개가 실제 선택한 근거 본문에 있는지 확인한다. 주요 명사는 현재 질문의 보통명사·고유명사에서 정해지며 사전에 등록한 약어와 풀이를 같은 용어로 인정한다. 명사와 식별자가 모두 없으면 불충분하다. 부족하면 한 번 더 검색하고 끝까지 부족하면 답변 작성을 부르지 않는다. 약어를 임의로 풀거나 관련 이름만 나열해 이 검사를 채우지 않는다(4.5·4.6).

문서 부모의 최종 근거 수는 초기 설정에서 최대 6개이다. `ai.gateway.search.evidenceLimit`의 허용 범위는 1~10이고 토큰 예산 때문에 더 적게 선택될 수 있다. 중복 사실이 근거 자리를 차지하지 않도록 한 사실은 한 곳에서 소유한다. 비문서 근거는 이 개수 상한과 별도로 남은 토큰 예산을 쓴다(4.5·4.7).

생성한 문장의 수치·식별자는 인용 본문과 완전히 일치해야 하고, 보통명사·고유명사·영문 이름은 인용 본문 또는 헤더에 있어야 한다. 수치의 단위 변환이나 추론상 같은 뜻을 자동 인정하지 않는다. 작성할 때 단위·대소문자·이름을 원천 그대로 보존한다. 링크는 표시 문자만 남고 주소를 열지 않으므로 링크 대상에만 답을 두지 않는다. 이 검사는 글자와 위치를 대조할 뿐 사실의 진실성·조건 관계를 증명하지 않는다(4.4 허용 구조 행·4.7 결정적 대조 표).

원본은 파싱 메모리에서만 다루고 저장·임베딩·검색·LLM에는 마스킹한 자료를 준다는 목표 계약이다. 현재 `ContentSanitizer`의 `mask-v1`은 Bearer 문자열, api key·password·passwd·secret·token의 값 표기, 이메일, 휴대전화 형태, 이름·성명·표시 이름 값 표기, SENTINEL 표식을 마스킹한다. 비밀값은 애초에 쓰지 않고, 일반 코드·숫자도 해당 형태와 겹치면 지워질 수 있으므로 마스킹 뒤 사실이 남는지 확인한다. 이유는 검색 원문이 맞아도 마스킹된 근거에 없는 값은 답할 수 없기 때문이다(4.4·`modules/ai-gateway-core/src/main/java/com/nori/ai/gateway/core/sanitize/ContentSanitizer.java`).

현재 `mask-v1`에서는 표 머리글이 `이름`·`성명`·`표시 이름`·`display name` 같은 이름 표기나 `api_key`·`api-key`·`apikey`·`password`·`passwd`·`secret`·`token` 같은 자격 표기로 끝나면 직렬화한 `머리글=값`에서 값까지 마스킹될 수 있다. 예를 들어 `설비 이름=EQP01`은 `설비 [마스킹]`으로 바뀐다. 문단의 `설비 이름: EQP01`도 같다. 이 규칙에 걸리는 머리글·값 표기를 피하고 대상에 맞는 `설비 ID`·`Secret 리소스` 같은 머리글을 쓴다. `설비 ID=EQP01`과 `Secret 리소스=tc-db-secret`은 현재 규칙에서 보존된다. 키 자체를 설명할 때도 `항목=token | 값=10초`처럼 항목과 값을 분리하면 이 표본은 보존된다. 이는 현재 클래스에 적용해 확인한 결과이며 모든 문자열의 마스킹 안전을 보장하지 않으므로 작성 후 실제 직렬화 본문에 적용해 다시 대조한다.

## 파일 위치와 열람 구획

버킷은 시스템별 저장 공간이고 prefix는 그 안의 객체 경로 앞부분이다. 시스템마다 버킷을 나누고 TC 채팅에서 nori-mes·nori-hrm 버킷을 검색하지 않는다. 다른 시스템과 주고받는 TC 계약을 설명하는 것과 다른 시스템의 내부 문서를 TC로 가져오는 것은 구별한다. 이유는 006 SPEC 4.4가 다른 시스템 원천을 합쳐 검색하지 않도록 정했기 때문이다.

| 시스템·버킷 | prefix | 필요한 권한 전부 | 넣는 내용 |
|---|---|---|---|
| TC·nori-tc | `00.rag/user/` | `[AI_DOC_READ]` | 화면에서 보거나 화면으로 조치하는 내용 |
| TC·nori-tc | `00.rag/admin/` | `[AI_DOC_READ, AI_ADMIN_DOC_READ]` | 클러스터·DB·Kafka·설정 파일 접근이 필요한 설치·운영·연동 내용 |

다른 시스템도 화면 사용과 내부 운영 접근을 같은 기준으로 구별하되 실제 버킷·권한 코드는 그 시스템 담당자가 확정한다. 문서는 소속 원천의 권한을 상속하며 메타 블록으로 개별 권한을 부여하지 않는다. 권한 배열의 코드는 모두 있어야 하므로 두 구획에 공통으로 필요한 사실은 user에 한 번만 둔다. user 문서는 admin 문서를 읽으라고 안내하지 않고 운영 담당자에게 넘길 증상·시각·대상·화면 결과를 적는다. 이는 4.1의 두 구획 결정과 4.3의 포함 검사에 따른다.

같은 시스템·같은 버킷에서 prefix가 같거나 한쪽이 다른 쪽의 문자열 앞부분이면 기동 오류이다. `00.rag/`와 `00.rag/user/`를 함께 등록하지 않는다. 빈 prefix도 같은 버킷의 모든 prefix와 겹친다. 다른 버킷의 같은 prefix는 허용한다. 이 검사는 현재 `GatewaySystemsProperties.SystemConfig`에도 있으므로 경로를 추가할 때 반드시 대조한다.

Gateway가 받는 형식은 객체 키가 `.md`로 끝나는 Markdown 파일뿐이다. xlsx·pdf·docx·xls·csv는 지원하지 않는다. 기존 자료는 사실을 확인할 원천으로 쓰고 검색 원문은 새로 쓴다. 이는 006 SPEC 4.4와 7절의 문서 형식 결정이다.

objectKey는 버킷 안의 파일 경로이다. 정한 prefix 뒤에 내용을 드러내는 영문 소문자 단어를 하이픈으로 이은 이름과 `.md`를 붙인다. 숫자가 실제 제품·프로토콜 이름의 일부일 때만 이름에 남긴다. 순번·작업 단계·목록 분류 코드는 파일명에 넣지 않는다. 예를 들어 TC 연결 모드 설명의 이름은 `00.rag/user/equipment-connection-mode.md`로 쓴다. 이는 Gateway가 `.md` 끝 외에는 요구하지 않는 작성 관례이며, 목록 번호가 바뀔 때 객체 식별과 revision 이력이 불필요하게 갈라지지 않게 한다.

파일은 BOM 없는 UTF-8, 줄끝 LF, Unicode NFC로 저장하고 CR·NUL을 넣지 않는다. 파일 바이트 상한 초기값은 `ai.gateway.documents.maxFileBytes=1048576`이며 양수이고 이 초기값이 허용 상한이다. 적용값보다 작거나 같아야 하며 상한까지 채우는 것을 권장하지 않는다. 이유는 4.4 파일·제한 행이 원문 줄과 정규화 결과를 보존하고 과대 파일을 파싱 전에 차단하기 때문이다.

## 허용하는 Markdown과 직렬화

직렬화는 Markdown의 장식을 걷어내고 검색할 글자로 바꾸는 과정이다. 글자 수는 마스킹 전 직렬화 본문의 Unicode 코드포인트 수로 센다. UTF-8 바이트 수·화면 폭·토큰 수와 혼동하지 않는다(006 SPEC 4.4).

| 항목 | Gateway가 받는 범위와 작성 방법 | 근거·이유 |
|---|---|---|
| 제목 | H1·H2만 허용한다. 첫 블록 H1 하나, H2 한 개 이상으로 쓴다. H1과 첫 H2 사이에는 허용된 메타 블록만 둔다. 작성 관례로 `# `·`## ` 표기만 쓴다. | 4.4 문서 제목·절 행. 제목 밑줄 표기와 일반 문장을 혼동하지 않도록 작성 표기를 좁힌다. |
| 문단·인라인 | 일반 문자·인라인 코드·강조·링크·줄바꿈을 허용한다. 문단의 인라인 문자는 이어 쓰고 줄 안 줄바꿈은 공백 하나, 강제 줄바꿈은 LF가 된다. 인라인 코드는 백틱 없이 원래 문자 그대로이다. 링크는 표시 문자만 남는다. | 4.4 허용 구조·본문 직렬화 행. 주소나 서식에만 의미를 싣지 않는다. |
| 목록 | 순서·비순서 목록을 허용한다. 비순서 항목 앞은 `- `, 순서 항목 앞은 원래 번호와 `. `이다. 항목 안 블록과 하위 항목은 LF로 잇고 최상위 항목 전체가 자식 하나이다. 작성 시 순서는 원문에 실제 진행 번호로 적는다. | 4.4 본문 직렬화·자식 청크 행. commonmark 0.32.0은 시작 번호만 보존하므로 원래 번호는 원문에서 확인한다(006 PLAN의 commonmark 실행 확인). 편집기 자동 번호만 믿지 않는다. |
| 표 | GFM 표이며 머리글 한 행, 자료 한 행 이상이다. 머리글은 빈 칸 없이 표 안에서 유일하고 자료 칸도 비어 있지 않아야 한다. 모든 자료 행의 실제 칸 수가 머리글과 같아야 한다. 자료 행은 `머리글=값`을 ` \| `로 이어 한 줄로 만든다. 행 사이 값 상속은 없다. | 4.4 표·본문 직렬화 행. 파서가 초과 칸을 버리고 부족 칸을 빈 칸으로 채우므로 원문 칸도 세며, 위 행의 값을 생략하여 뜻을 이어받게 하지 않는다. |
| 펜스 코드 | 펜스 코드 블록을 허용하며 내용 줄을 그대로 둔다. 작성 관례로 시작·끝 울타리를 모두 쓰고 코드 설명과 실행 조건은 같은 절에 둔다. | 4.4 허용 구조·본문 직렬화 행. 닫지 않은 펜스가 문서 끝까지 코드로 읽혀 다음 절이 삼켜지는 일을 막는다(006 PLAN의 commonmark 실행 확인). |
| 블록 사이 | 본문 블록 사이는 LF 하나로 잇는다. 자식은 1~200자, 부모는 1~450자, 각 제목은 1~60자로 확인한다. | 4.4 본문 직렬화·자식 청크·부모 청크·문맥 헤더 행. 원문 빈 줄 수로 직렬화 길이를 계산하지 않는다. |
| 금지 구조 | H3 이하 제목·raw HTML·이미지·인용 블록·들여쓰기 코드 블록·구분선·링크 참조 정의와 그 밖의 노드를 넣지 않는다. | 4.4 허용 구조 행. 표준 Markdown에서 보이는 것만으로 지원한다고 판단하지 않는다. |

표의 파이프 문자가 값의 일부이면 이스케이프하고, 장식용 빈 칸이나 병합을 흉내 낸 행을 쓰지 않는다. 각 자료 행이 단독 자식이므로 대상·단위·조건을 그 행과 헤더만으로 읽을 수 있어야 한다. 이는 4.4의 행 단위 직렬화와 빈 칸 금지에 따른 작성 방법이다.

## rag-meta 기록 형식

정보 문자열이 정확히 `rag-meta`인 펜스 코드 블록을 H1 바로 뒤와 각 H2 바로 뒤에 하나씩 둔다. Gateway는 각 위치에 하나까지 허용하며 내용을 해석하지 않는다. 이 작성 규칙은 원천 추적을 위해 두 위치의 블록을 필수로 한다. 검색·임베딩·LLM 본문에서는 빠지지만 버킷을 읽는 사람에게 보이므로 비밀값·개인 연락처를 쓰지 않는다(006 SPEC 4.4 메타 블록 행).

문법은 한 줄에 `키: 값`이다. 구분자는 처음 나오는 콜론과 공백 하나이고 값은 비어 있지 않은 한 줄 문자열이다. 들여쓰기·여러 줄 값·같은 키 중복·아래에 없는 키를 쓰지 않는다. `원천`만 여러 번 쓸 수 있으며 여러 근거를 같은 값에 뭉개지 않는다. 이는 YAML을 해석하는 계약이 아니라 작성자끼리 같은 방식으로 읽기 위한 관례이다.

| 위치 | 키 | 필수 여부·값 | 이유 |
|---|---|---|---|
| H1 뒤 | `유형` | 필수. `사용 절차`·`개념`·`운영`·`트러블슈팅`·`알려진 제약`·`참조`·`FAQ` 중 하나 | 4.9 최초 정답 세트는 이 값을 기준으로 유형을 센다. |
| H1 뒤 | `적용` | 필수. 대상 제품·판본·프로토콜 조건을 적는다. 저장소 파일 판본이면 확인한 commit 또는 파일 SHA-256을 명시한다. | 현장 배포 판본으로 오인하지 않게 한다. |
| H1 뒤 | `확인일` | 필수. `YYYY-MM-DD` | 언제 대조했는지 구별한다. 자동 유효기간을 뜻하지 않는다. |
| H1 뒤 | `담당` | 필수. 개인 정보 대신 유지보수 팀·역할 이름 | 원천 변경 시 확인할 책임을 남긴다. |
| H1 뒤 | `관련문서` | 선택. 같은 구획 또는 user의 objectKey 하나를 한 줄에 적는다. | 위치 안내만 하며 답 근거를 링크로 대신하지 않는다. |
| H2 뒤 | `원천` | 필수·반복 허용. `저장소/상대경로 @ 판본 ; 위치` 형식. 판본은 commit 해시 또는 `sha256=` 뒤 파일 해시, 위치는 심볼과 원문 줄 범위 또는 문서 절 이름이다. | 절의 각 사실을 실제 근거에 다시 대조할 수 있게 한다. |
| H2 뒤 | `적용` | 선택. 문서보다 좁은 조건 | 조건이 답변에 필요하면 본문에도 그 조건을 쓴다. 메타는 검색되지 않는다. |

원천이 다른 사실을 한 절에 쓸 때는 원천을 각각 기록하고, 검토 기록에서 사실과 원천을 대응시킨다. 코드 경로만 적고 읽지 않거나 매뉴얼을 코드 근거처럼 기록하지 않는다. 이유는 이름 토막 뜻풀이 결함에서 선언 이름·타입만으로 뜻을 만들어냈기 때문이다.

## 유형에 따라 절을 나누는 법

아래 순서는 각 절에서 답을 완결하는 순서이다. 모든 파일에 같은 H2 제목을 찍어내는 틀이 아니다. 실제 질문·작업·증상에 맞는 제목을 직접 쓴다. 이는 틀로 찍은 제목과 정보 없는 틀 문장의 반복을 막는다.

| 유형 | H2 하나가 다루는 것과 절 안의 순서 | 450자를 넘을 때 나누는 법 |
|---|---|---|
| 사용 절차 | 화면 작업 하나. 대상·선행 권한과 조건 → 실제 화면 조작 순서 → 결과 확인 → 실패 시 사용자가 확인하고 넘길 정보 | 독립해서 시작·확인 가능한 작업 경계로 나눈다. 저장과 배포처럼 결과가 다른 작업은 각각 제목을 붙이고 필요한 조건만 함께 둔다. 긴 목록 항목도 200자 안에 든다. |
| 개념 | 개념 하나 또는 비교 관계 하나. 정의 → 적용 대상·경계 → 구별할 개념과 관찰 방법 | 정의와 독립 비교 질문을 나누되 대명사 대신 대상을 다시 명시한다. 이름마다 같은 설명을 반복하지 않는다. |
| 운영 | 운영 작업 하나. 적용 판본·권한·선행 상태 → 조작 → 성공 확인 → 실패·중단·되돌림 조건 | 독립 작업 또는 실패 분기로 나누고 각 절에 실행 조건을 둔다. 위험한 명령만 떼어 놓지 않는다. |
| 트러블슈팅 | 증상 하나와 그 증상을 가르는 확인 경로. 관측 증상 → 원인 후보와 구별 증거 → 확인 순서 → 조건별 조치·인계 → 수정 적용 판본 | 별도 증상이나 별도 판별 경로로 나눈다. 원인 하나를 확정하려면 실제 근거가 있어야 하고 재시작을 공통 해결책으로 붙이지 않는다. |
| 알려진 제약 | 제약 하나. 해당 판본·조건 → 실제 제한 → 영향 → 확인된 우회 경로 또는 담당자에게 넘길 정보 | 서로 다른 제한으로 나눈다. 화면 안내의 틀린 주장은 옮기지 않고 정확한 화면 명칭과 실제 제한만 쓴다. |
| 참조 | 같은 질문에 답하는 코드·값·설정의 의미 묶음 하나. 대상·조건 → 이름·값·단위와 의미 → 발생·사용 조건 → 확인·조치 | 의미가 다른 묶음으로 나눈다. 표는 행별 200자, 절 전체 450자를 확인하고 번호로 잘라 제목만 바꾸지 않는다. |
| FAQ | 다른 절이 소유하지 않는 질문 하나. 구체 질문을 제목으로 → 올바른 답 → 적용 조건·확인 방법 | 서로 다른 질문으로 나눈다. 한 질문의 답이 길면 적합한 업무 유형으로 옮기고 FAQ에 복제하지 않는다. |

공통 FAQ 문서는 여러 업무에 걸친 오해 정정에만 쓴다. 영역별 FAQ는 해당 업무 문서 안의 고유한 질문 제목 H2로 두되 이미 작업·증상 절이 답하는 질문은 그 절을 보완한다. FAQ라는 이유로 본문을 복사하지 않는다. 이유는 본문 복제 결함에서 업무 본문이 FAQ에 복제되어 검색 후보를 중복으로 채웠기 때문이다.

## 절과 문장을 쓰는 기준

절 하나와 문맥 헤더만 읽어도 주체·적용 조건·답·확인 방법을 알 수 있게 쓴다. “위와 같다”, “해당 작업에 적용한다” 같은 정보 없는 말로 시작하지 않는다. 단, 공통 사실의 본문을 반복하지는 않고 각 절에 필요한 최소 조건만 적는다. 사실의 소유 절을 정하고 다른 절에서는 그 사실을 새 답처럼 복제하지 않는다. 이유는 부모 단위 제공과 근거 상한, 본문 복제·정보 없는 틀 문장 결함 때문이다.

화면 문구·코드·상태·단위·대소문자는 원문 그대로 쓴다. 화면 기능은 렌더 코드와 실제 언어 문구, 호출 API와 처리 코드를 함께 확인한다. 설정 키를 단어로 쪼개 번역하거나 상태 이름만 보고 뜻을 짓지 않는다. 사용처가 의미를 밝히지 않으면 그 뜻은 쓰지 않는다. 이는 4.7의 문자 대조를 지키고 이름 토막 뜻풀이를 막기 위한 기준이다.

판본·모델·프로토콜에 따라 달라지는 조건은 본문에도 쓴다. 현장의 현재 접속 상태·설정값·WORK·LOT·배포 판본·연락처·백업 시각을 저장소 설명으로 확정하지 않는다. 고친 장애는 확인한 변경을 기준으로 “해당 수정 이후 판본에서 고쳐짐”으로 적고 현장 적용 여부와 구별한다. 변경이 실제 어떤 실패를 고쳤는지는 커밋 제목만 보지 않고 변경 코드·관련 시험과 대조한다. 이유는 [TC 문서 목록](tc-rag-document-list.md)에 기록한 현장 판본 부재와 4.4의 재기동 때만 갱신되는 정적 원문 성격 때문이다.

비밀값과 틀린 문장을 본문·예제·메타에 넣지 않는다. 오답을 인용한 뒤 부정하는 방식도 쓰지 않고 정확한 사실만 쓴다. 평가용 오답 사례와 검토 기록은 검색 원문 밖에 둔다. 4.7 검사는 문자 대조라서 틀린 문장도 글자가 있으면 통과할 수 있고 틀 오답 결함에서는 실제로 같은 틀의 오답까지 만들어냈기 때문이다.

원천 없는 사실은 반입 본문에서 생략한다. “현장 확인 필요”로 빈 답을 채우지 않는다. 빠진 항목과 확인할 담당 역할은 작성 목록·검토 기록에 남기고 근거를 확보한 뒤 추가한다. 확인된 일반 절차만으로 독립 답이 되면 그 절차는 남긴다. 이유는 4.9의 답할 수 없는 문항은 실제 정답 부재를 확인하며, 미확인 값이나 추정 문장을 넣으면 4.7의 글자 대조가 그 문장을 근거로 삼을 수 있기 때문이다.

## 원천 확인과 기록

동작은 코드를 1차 근거로 확인한다. 진입점 → 호출·피호출 → 상태 변경 → 외부 입출력·설정 → 결과를 좁게 추적하고 관련 시험의 기대값도 읽는다. 매뉴얼·설계 문서는 이 흐름과 대조한 사실만 쓰며 문서에 있다는 이유로 동작을 확정하지 않는다. 코드가 결정하지 않는 업무 의미·제조사 계약은 승인된 업무·제조사 원본이 필요하다. 이는 [TC 문서 목록](tc-rag-document-list.md)에 기록한 제조사 사양 부재와 이름 토막 뜻풀이를 구별하기 위한 기준이다.

절별 rag-meta에 확인한 원천 판본과 위치를 남기고 파일 해시 또는 commit에 연결한다. 작성 기록에는 사실별 대조 결과·미확인 부분·중복 사실 소유 절을 남긴다. 원천이 바뀌면 영향받는 절부터 재확인한다. 이는 숫자만 본 자체 검사처럼 숫자·링크 검사만으로 품질을 판정하지 않게 한다.

## TC 사실로 확인한 형식 예시

다음은 `nori-tc-gateway`의 `ConnectionMode.fromText` 구현과 대조한 짧은 참조 예시이다. 적용은 메타에 기록한 소스 판본이며 현장 배포를 확인했다는 뜻이 아니다. 대소문자 변환과 지원하지 않는 값·null·빈 값의 거절은 해당 메서드 본문에서 확인한다. GFM 표 칸의 앞뒤 공백은 사라지므로 공백 제거는 문장으로 설명한다.

````markdown
# TC 연결 모드 입력
```rag-meta
유형: 참조
적용: nori-tc-gateway ConnectionMode.java sha256=49d629962b31bb98d1771baaa8bf49f69eef4a91f381d63de110a506fa57f5c2
확인일: 2026-11-18
담당: TC 문서 담당
```

## 연결 모드 문자열 처리
```rag-meta
원천: nori-tc-gateway/gateway/tc-gateway-core/src/main/java/com/nori/tc/gateway/core/db/ConnectionMode.java @ sha256=49d629962b31bb98d1771baaa8bf49f69eef4a91f381d63de110a506fa57f5c2 ; ConnectionMode.fromText L30~45
```

ConnectionMode.fromText는 앞뒤 공백을 제거하고 대문자로 바꾼다.

| 입력 | 처리 결과 |
|---|---|
| aCTIVE | ACTIVE로 변환한다. |
| UNKNOWN | 오류로 거절한다. |

지원하지 않는 값, null, 빈 문자열은 오류로 거절한다.
````

나쁜 예시는 앞의 작성 결함 표에 적은 “에 관한 짧은 확인” 같은 반복 제목, “적용: 문서 제목의 해당 작업.” 같은 빈 문장, 키 이름의 낱말을 가운데점으로 이은 뜻풀이이다. 이것들은 이 안내에서 결함을 식별하는 표현이며 검색 원문에는 옮기지 않는다. 고치는 방법은 원천이 답하는 질문을 제목으로 직접 쓰고 사용처가 밝히는 의미만 적어 틀로 찍은 제목·이름 토막 뜻풀이·정보 없는 틀 문장을 없애는 것이다. 틀 오답을 막기 위해 틀린 업무 주장은 나쁜 예시로도 재수록하지 않는다.

## 작성 후 검사와 합격 판단

검사 기록에 대상 파일의 해시, 명령·도구 버전, 확인한 실제 수, 지적 위치와 수정 결과를 남긴다. 자동 검사 뒤에는 원천과 문장을 사람이 대조한다. 스크립트로 제목·본문·FAQ를 틀에 찍어 생성하지 않는다. 이유는 앞의 여섯 작성 결함의 공통 원인이 틀 생성과 숫자만 본 자체 검사였기 때문이다.

| 검사 | 세고 읽는 방법과 합격 조건 | 막는 지난 결함 |
|---|---|---|
| 파일·구조·길이 | 파일마다 인코딩·BOM·CR·NUL·NFC·바이트 수, 금지 노드 수, H1 수·첫 블록, H2 수·유일성, 메타 위치·키·유형을 전수 확인한다. 마스킹 전 직렬화 자식·부모·제목 길이를 모두 세고 위반 0건으로 한다. 표 원문 각 행의 칸 수·빈 칸·중복 머리글과 목록 원래 번호도 대조한다. | 숫자만 본 자체 검사. 구조 검사만으로 의미가 맞다고 판단하지 않는다. |
| 제목 | 전체 제목의 정확 중복과 식별자를 지운 모양을 모은다. 같은 모양이 3회 이상이면 목록과 정당한 이유를 적고 불필요한 틀 반복은 0건으로 고친다. “니다의”·“에 관한 짧은 확인”·“의 의미와 확인”·“· 관련 항목” 형태 제목은 0건으로 한다. | 틀로 찍은 제목·숫자만 본 자체 검사 |
| 본문·사실 중복 | 메타·공통 적용 문구를 제외한 같은 본문을 묶어 세고, 문장이 달라도 같은 사실인 절을 전수 대조한다. 각 사실의 소유 절은 하나로 정하고 답 본문의 복제 0건으로 한다. | 본문 복제·숫자만 본 자체 검사 |
| 빈 틀 문장 | 반복 문장을 뽑고 사실·조건·조작·결과를 추가하지 않는 문장을 표시한다. 항목 이름만 바뀌는 문장까지 읽어 정보 없는 반복 0건으로 한다. | 정보 없는 틀 문장·숫자만 본 자체 검사 |
| 뜻풀이 | 설정·상태·코드 설명을 사용처에 전수 연결한다. 이름 토막을 나열한 뜻풀이와 사용처 근거 없는 의미 0건으로 한다. | 이름 토막 뜻풀이·숫자만 본 자체 검사 |
| 문장·오답 | 모든 제목·문장을 읽어 조사 접합 오류·주어 소실·잘린 문장·틀린 주장·오답 사례 0건을 확인한다. 마스킹 전후 의미와 원문 표기를 대조한다. | 틀로 찍은 제목·틀 오답·숫자만 본 자체 검사 |
| 마스킹 적용 결과 | 현재 mask-v1을 직렬화 본문 전체에 적용하고 전후를 대조한다. 이름·성명·자격 값 형태의 머리글과 콜론 문장을 전수 확인하여 필요한 값이 사라지는 곳을 세고, 의미에 맞는 머리글·문장으로 고쳐 미해소 0건으로 한다. | 숫자만 본 자체 검사. 원문 글자가 있어도 실제 근거에서 사라질 수 있다. |
| 권한 경계 | user 파일에서 admin objectKey·링크·관리 문서 열람 지시를 찾아 0건으로 한다. 관리 전용 답 사실이 user에 없는지도 전수 확인한다. 필요한 인계 정보로 고친다. | 본문 복제·숫자만 본 자체 검사. 2026-11-18 사용자가 확정한 TC 문서의 구획 결정도 지킨다. |
| 사람이 읽는 무작위 표본 | 전체 절에서 무작위 40절을 고르고 40절 미만이면 전부 읽는다. 추출한 절 목록을 보존하고 제목만으로 질문을 아는지, 원천과 맞는지, 독립 답인지, 다른 절과 겹치는지 각각 판정한다. 미해소 지적 0건으로 하고 수정 영향 부분을 다시 확인한다. | 앞의 여섯 작성 결함. 숫자 검사의 빈틈을 사람이 확인한다. |

표본 검사는 전수 형식·사실 검사를 대신하지 않는다. 마지막 편집 후 문서·절·유형·구획 수를 다시 세고 전체 diff와 원천 대조를 읽는다. 미확인 부분은 합격으로 세지 않는다. 이것이 숫자만 본 자체 검사에서 빠진 사람의 품질 확인을 보완하는 방법이다.

## 반입과 갱신

1. 작성·검사한 원문 판본과 objectKey·구획을 고정한다. TC는 `nori-tc` 버킷의 `00.rag/user/` 또는 `00.rag/admin/`에 둔다. 평가 질문·정답·오답 사례·검토 기록·이 안내와 목록은 검색 prefix 밖에 보관한다. 이유는 4.9의 평가 근거와 검색 원문을 분리하고 틀린 근거 유입을 막기 위해서이다.
2. 실제 반입 작업에서는 담당자가 두 원천 설정과 구현 적용을 확인한 뒤 해당 위치에 올리고 Gateway를 정상 절차로 재기동한다. 이번 문서 작성 작업에서는 업로드·설정 수정·재기동을 하지 않는다. 4.4가 실행 중 파일 동기화를 하지 않기 때문이다.
3. 동기화 뒤 제외 기록의 objectKey·줄·사유와 실제 반입 목록을 대조한다. 006 SPEC 4.4·5절은 이 메타데이터 보존만 정하며 조회 API·화면·명령은 정하지 않는다. 현재 연결된 코드는 문서 상태를 UNKNOWN으로 반환하므로 지금 사용할 제외 조회 수단을 제시할 수 없다. 구현 후 실제 제공되는 점검 수단을 확인하고 그 전에는 검색 반영 성공으로 기록하지 않는다.
4. 규칙 위반 파일 제외와 동기화 장애를 구별한다. 파일 제외는 묶음 실패가 아니며 prefix의 객체 0개도 정상 0문서이다. 반면 S3 열거·다운로드·지원 파일 파싱 실패나 임베딩·저장 실패는 새 묶음을 활성화하지 않고 readiness를 닫는다. 응답이 나왔다는 이유로 모든 파일의 반입을 성공 처리하지 않는다(4.4·5절).
5. 수정·삭제 뒤에는 실제 파일 바이트 SHA-256인 revision과 원문 줄이 바뀌는지 확인한다. ETag를 내용 해시로 쓰지 않는다. 옛 파일을 같은 검색 prefix에 백업으로 남기지 않고 검색 원문 밖에서 이력을 관리한다. 이유는 4.4가 현재 원천을 열거해 새 묶음으로 전환하기 때문이다.
6. 새 revision 활성화 후 옛 근거의 검증된 답변은 신규 재사용 대상에서 빠지지만 당시 답변·마스킹 근거 스냅샷은 보존된다. 정답 세트는 옛 revision을 그대로 최신 문서 평가에 쓰면 입력 오류이므로 변경된 원문·직렬화 사실·자식 줄 범위를 다시 확인하여 새 세트 버전을 만든다. 원래 문항과 과거 검토 이력을 덮어쓰지 않는다(4.4·4.8·4.9).
7. DOCUMENT 조치가 표시한 보완 대상 중 하나라도 revision이 달라지거나 문서가 없어지면 재기동 동기화에서 해당 답할 수 없는 문항이 비활성화된다. 문서 보완 후 같은 피드백을 새 version으로 검토해 기대값을 갱신한다. RETRIEVAL·ANSWER의 교정 답변도 현재 문서 위치와 4.7 대조를 다시 충족해야 한다. 검토 API가 원본 문서를 직접 고치지는 않는다(4.8).

갱신 후 평가는 4.9에 따라 문서·세트·설정 판본에 결속하여 수행한다. TC 최초 구성은 답할 수 있는 30문항, 답할 수 없는 15문항, admin에만 근거가 있는 권한 5문항이다. 유형은 H1 뒤 메타의 일곱 유형으로 나누고 권한 문항의 답이 user에 복제되지 않았는지 확인한다. 답할 수 없는 문항은 정답 부재를 실제 전체 허용 자료에서 확인한다. 문서 형식 합격과 실제 정답률 실측은 별개이며 이 문서 작성으로 정답률을 입증하지 않는다.

## 새 문서와 새 시스템 추가

새 문서는 실제로 답할 질문과 원천이 있고 기존 소유 절로 답할 수 없을 때 목록에 추가한다. 질문·필요 이유·원천·미확인 부분·유형·구획·내용 기반 objectKey를 먼저 정하고 본문을 작성한다. 같은 규칙을 쓰는 설비는 같은 문서를 공유하며 설비 대수만 늘었다고 복제하지 않는다. 실제 계약·모델·프로토콜 차이는 확인한 적용 조건으로 구별한다. 제조사 원본이 없는 설비 사양은 이름만 보고 추가하지 않는다. 이는 2026-11-18 TC 문서 목록 조사·사용자 확정의 제조사 사양 제외 결정과 2026-11-13 TC 문서 준비 때 정한 공통 지식 공유 결정을 유지하고 이름 토막 뜻풀이·본문 복제를 막기 위한 절차이다.

새 시스템은 담당자가 시스템 ID·전용 버킷·화면/운영 구획·실제 권한 코드·원천 소유자와 판본을 확인한다. 기존 시스템 버킷을 공유하거나 TC 권한 코드를 자동 이식하지 않는다. 시스템 등록·원천 설정 변경은 별도 구현·운영 작업에서 수행하고 문서 작성자는 겹치지 않는 경로와 권한을 전달한다. 이후 같은 Markdown·원천·품질 검사를 적용하고 재기동·제외 확인·그 시스템 정답 세트 평가를 수행한다. 이유는 4.1·4.4·4.9가 시스템별 인증 범위·검색·평가를 분리하기 때문이다.
